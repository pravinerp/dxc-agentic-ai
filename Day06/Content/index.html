Concept 2 · INTERMEDIATE

Middleware: guards that run around the model and the tools

Yesterday you pasted checks into the loop: the step limit, the repeat guard, error handling. Middleware gives those checks a proper place. You write the check; LangChain decides when it runs.

Two hook points matter today. Click through one full round.
🛡️ before_model
Runs just before each model call. It can look at the conversation, change it, or stop the whole run.
🧠 Model
Sees only what the guard let through. Asks for a tool, or answers.
🛡️ wrap_tool_call
Runs around each tool call: your code can catch errors, log, or block the call.
🔧 Tool
The real function runs.
🔁 Repeat
Back to before_model for the next round, until the model answers or a guard stops the run.

Three guards today: pii_guard and budget_guard (both before the model) and tool_guard (around tools). You write the logic for each.

pii_guard: personal data should not travel to a model if it does not need to. Type something personal, switch the guard on and off.
What the model receives:

Ticket and employee ids stay: the agent needs them. This is a simple pattern match: real systems add more patterns and a review.

budget_guard: yesterday's step limit, now as middleware. When the limit is hit it adds a handover message and ends the run.
Model calls made by a stuck agent0
Input tokens paid for (illustrative)0
tool_guard: a tool crashes (the ticket database is down). Compare the two outcomes.

Same idea as Day 5's run_tool: an error becomes information, not a crash.

Concept 3 · INTERMEDIATE

Streaming, and what AWS logs for you

An agent can take ten seconds and several steps. A user staring at a blank screen assumes it is broken. Streaming shows each step as it happens.

Same agent, same total time (6 seconds, compressed). Press Run both.
⏳ invoke: wait for everything
Waiting...

Waiting...
First sign of life, invoke-
First sign of life, stream-
LangChain offers more than one view of the same run. You use two.

Steps help while tools run. Words help while the final answer is written. Real products often show both.

Trainer demo. Your accounts are Bedrock-only, so the trainer shows this in the AWS console. Streaming shows you the run; logging records it for operations.
⚙️ Turn on
Model invocation logging is a Bedrock setting. You choose where records go: CloudWatch Logs, an S3 bucket, or both.
🧾 What is recorded
Each model call: which model, when, how many input and output tokens, how long it took, and (if you enable it) the prompt and the response.
🔎 What you do with it
Query the logs: calls per hour, tokens per team, the slowest calls. That is how you find a looping agent after the fact.
🔒 Be careful
Prompts may contain personal data. Decide who can read the logs and how long they are kept. This is why the pii_guard matters.
