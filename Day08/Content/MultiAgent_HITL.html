Idea 1 · One agent or a team?

Multi-agent is a design choice, not an upgrade

One agent with 30 tools and a 3-page prompt gets confused and is hard to own. A team of small agents is easier to test and govern, but costs more calls and has more moving parts.

Tap each card

Quick decision rule

Ask yourselfIf YES
Does one prompt try to do very different jobs?Split into specialists
Do different teams own different parts?Split by owner
Must a human approve some actions?Add an approval step (any pattern)
Is the task simple and the same every time?Stay with ONE agent, or even a plain workflow
Say this: "Start with one agent. Split only when a measurement (wrong tools, cost, ownership, risk) tells you to."
Quick check · Idea 1

Three questions

1. What is the main COST of moving to multi-agent?
Each extra agent hop is another call and another place to fail.
2. Which is a good reason to split one agent into specialists?
Split for a measured reason: confusion, ownership, parallel work or risk. Long chats are a memory problem (Day 7).
3. A task is simple and identical every time. Best design?
Don't add agents to a problem that does not need them.
Idea 2 · Four coordination patterns

Pick the pattern by the problem

Router: an LLM classifies, ONE specialist runs.
Subagents: the main agent calls helpers like tools; each has its own small context.
Handoffs: control moves to another agent, which then talks to the user directly.
Skills: ONE agent loads extra instructions only when needed.
PatternWho talks to the user?StateUse it forWatch out
RouterThe chosen specialist (or a final step)Usually stateless per requestClear categories: tickets, intentsA wrong route = a wrong answer; add a fallback
SubagentsThe main agent onlyMain keeps state; subs are statelessIsolated jobs, parallel work, different ownersMore calls; the main agent must merge results
HandoffsWhichever agent has control nowStateful: who is 'on' is savedLong chats that change topicHarder to trace who said what
SkillsThe one agentOne agent's stateMany small capabilities, one voiceOne agent still owns everything
Today's lab uses Router + Subagent-style specialists + a human approval step. Frameworks such as CrewAI, OpenAI Agents SDK, Claude Agent SDK and Google ADK implement the same four ideas with different names.
Quick check · Idea 2

Three questions

1. AskIT reads a ticket and sends it to the Network OR Access OR Hardware agent. Which pattern?
An LLM classifies the input and ONE specialist runs.
2. A sales bot passes the customer to a billing agent, which then chats with the customer directly. Which pattern?
Control moves to another agent that talks to the user.
3. One agent loads the 'VPN troubleshooting' instructions only when a VPN question arrives. Which pattern?
Skills load extra context on demand into ONE agent.

Quick check · Idea 3

Three questions

1. What does the checkpointer do?
Saved state is what lets the graph pause for a human and resume after a crash.
2. Who should decide whether a password reset needs approval?
Policy must be predictable and auditable. An LLM can be talked into anything.
3. The approver answers two days later. What happens?
The state was checkpointed; resume continues from the pause.
Before the lab · How the app works

What happens behind the Control Room

One Streamlit app runs this graph. Follow the numbers.

The app you will use. The picture in the app lights up green / amber / red as your ticket moves.
  1. You pick a sample ticket and press ▶ Send to AskIT. The app starts the graph with a new id. app.py
  2. Router: ONE LLM call reads the ticket and returns a team name. multi_agent.py · router()
  3. A conditional edge sends the state to ONE specialist: a small agent with its own prompt and READ-only tools. make_specialist()
  4. Policy: plain Python decides if a human must approve (password reset; VIP rule after the curveball). policy()
  5. Human approval: interrupt() pauses the graph. The checkpointer saves everything. The app shows Approve / Reject. human_approval()
  6. Your click resumes the graph. Act runs the write tool ONLY if you approved. act() · reset_password
  7. Respond builds the reply. The trace shows every node, its tokens and time. respond()

Architect skill · 3 minutes

What is an ADR, and why do clients care?

An Architecture Decision Record is one page about ONE important decision: what we decided, what we rejected, and what it costs. Review boards (ARB) and clients read it before they approve money or go-live. On Day 1 you wrote one on model choice. Today your team writes a real one, with lab numbers.

A finished example (read it in 1 minute)

ADR-EXAMPLE: Which model powers AskIT's router? · Status: Accepted

Context: the router makes ONE short classification per ticket (Network / Access / Hardware / General). 10,000 tickets a day. It must answer in under a second.

Decision: use a small model (Amazon Nova Micro) for the router.

Alternatives rejected: Claude Sonnet: better on vague tickets, but many times the price per token for a one-word answer. Nova Lite: a middle option, keep as plan B if accuracy drops.

Evidence: routed all 6 Lab 8 test tickets to the right team; a few hundred tokens per ticket.

Consequences: + lowest cost and latency. − vague tickets may be misrouted → they fall back to General and a human. Revisit if misroutes go above 5%.

ADR partAnswers the question
ContextWhat problem, what limits, what did the client ask?
DecisionWhat did we choose? One sentence.
AlternativesWhat else did we consider, and why not?
EvidenceWhich numbers support it?
ConsequencesWhat do we gain, what do we pay, when do we revisit?
