Concept 1 · BASIC → INTERMEDIATE

What is an agent? What is a tool?

An agent is a model that can ask for tools and keep going until the job is done. The model never runs anything itself: it only asks. Your code runs the tool.

RAG vs agent: RAG alone always follows one fixed path (search, then answer). An agent chooses its next step each time. And RAG does not disappear: inside an agent, RAG is just one of the tools (our search_kb). The agent decides when to use it.
📚 RAG pipeline
question → search → answer
Same path every time. Predictable. Cannot change anything.
🤖 Agent
question → decide → tool → decide → tool → answer
Path depends on the question. Can act. Needs limits.

Three parts, nothing more

ReAct = Reason + Act. Each turn the agent thinks, acts with a tool, then observes the result. Click through one real AskIT question.
Question: "Priya left her laptop at the airport (ticket TKT-0046). What should she do, and how fast will we respond?"
💭 Think

🔧 Act

👁️ Observe

Now I need the lost-device rule.

👁️ Observe

💭 Think

✅ Answer
"Call the helpdesk now; the device will be locked and wiped [KB-014]. Critical tickets get a first response in 15 minutes [KB-016]."

Day 4's critic loop was a fixed recipe. Here the model chooses each action. That is the whole difference.

The most important idea of the day: the model does not run your tool. It sends a request. Your code runs the tool and sends the result back. Click through one round trip (this is the Bedrock Converse API that you use in Lab 5A).
1️⃣ App → Model
Your code sends the question and the list of tools (name, description, inputs).
2️⃣ Model → App
The model replies with a tool request: "please run get_ticket with ticket_id = TKT-0004" and a request id. Stop reason: tool_use. Nothing has run yet.
3️⃣ Your code
Your code finds the Python function and runs it. The model is not involved.
4️⃣ App → Model
Your code sends back a tool result with the same request id, so the model can match answer to question.
5️⃣ Model → App
The model reads the result and writes the final answer. Stop reason: end_turn. Or it asks for another tool, and we go round again.

Three message pieces to remember: the user message, the model's toolUse request, and your toolResult reply.

Only four tools, all day, every session. Two read, two change data. The model sees only the name and description, never the code, so write them well.
For every question the agent picks one path. It reads your question and the tool descriptions, then decides. These are the paths. AskIT has 5 of them today.
1. Answer from its own knowledge AskIT: yes
No tool. General or chat questions, like "Hi" or "What is a VPN?"
2. Look it up in documents (RAG) AskIT: search_kb
"How do I fix VPN error 809?" The answer is written in an article.
3. Read exact data (database / API) AskIT: get_ticket
"What is the status of TKT-0004?" One exact record, no guessing.
4. Take an action AskIT: update_ticket, reset_password
Changes something. Needs a human to approve first (Lab 5C).
5. Hand over to a human AskIT: step limit, VIP rule
Stuck, risky or a VIP. The agent stops and a person takes over.
6. Search the internet not in AskIT
For fresh facts the company documents do not have.
7. Calculate not in AskIT
A calculator or code tool. Models are weak at exact maths.
8. Ask another agent not in AskIT
A specialist agent does part of the job.
9. Ask the user a question not in AskIT
"Which ticket do you mean?" when information is missing.

RAG or a database tool? A simple rule

Need a list, a number or one exact record?
Use a database tool (a SQL query or an API).
"How many Critical tickets are open?" RAG could miss or invent rows.
Need an explanation or a similar past case?
Use RAG over text.
"How was a similar VPN problem solved?" Put the text of the notes in RAG.

A real agent often has both and picks per question. You only attach a database to RAG when the useful content in it is long text (ticket notes, resolutions) that people search by meaning.

The agent loop and its stop rules

A loop is powerful and dangerous in one breath. Every agent loop needs a way to finish and a way to give up.

Pick a question, press Next step. Scenario C is the dangerous one: the tool never gives a useful answer. Move the step limit and see what changes.
Scenario: Step limit6
Steps used0
Input tokens so far (illustrative)0
Three exits. Build all three, because any one of them can fail.

Tool errors are information

If a tool fails ("ticket not found"), do not crash. Return the error as the tool result. The model reads it and explains, or tries different inputs. That is why your run_tool catches every exception.
Every step resends the whole conversation. So cost grows faster than the step count. Illustrative numbers: your Lab 5C run shows the real ones.

Safe tools, and the same loop on any model

Reading is low risk. Changing things is where agents hurt people. Put the safety in code around the tool, never only in the prompt.

Sort the four tools by what they can damage. Switch the approval rule on and off and ask for a password reset.
ToolChanges data?Rule
search_kbNoRuns freely
get_ticketNoRuns freely
update_ticketYesA human approves
reset_passwordYesA human approves
Where the check lives: between the model's request and the tool. The model cannot skip it.
🧠 Model
Asks for reset_password with EMP-1021.
🛡️ Your code
Does this tool change data? Yes, so it pauses.
🙋 Human
The agent shows what it wants to run. A person answers y or n.
✅ If yes
The tool runs and the result goes back to the model.
⛔ If no
The tool does not run. The model gets an error: "not approved, do not retry". It tells the user a human will follow up.

"AskIT has been working on one ticket for five minutes"

The Orbit Corp CIO just messaged: "The bill is climbing and the user still has no answer. Find out why. Fix it."

What we doSwitch a bug on. Run the agent and watch it ask the same thing again and again. Find out why. Then switch the fix on (change one word).
WhyAgents can get stuck in a loop and quietly burn money. The step limit stops the loop, but only after every step has been paid for.
Outcome / learningYou can say in one sentence why the agent kept repeating, and the agent now stops itself after 2 steps.
HowSwitch bug on and run (5 min) → write what you saw (2 min) → switch fix on and run (3 min).
  1. Wait for the trainer to say GO. Then in VS Code click File → Open File, paste C:\AskIT\dxc-agentic-ai\.env and press Enter. Add a new line at the bottom: ASKIT_INCIDENT=loop and press Ctrl+S. Go back to agent.py.
  2. Run this and count the steps: python run_agent.py "What is the status of ticket TKT-0004?" You should see the same get_ticket line again and again, then a hand over after 6 steps.
    Answered in 1 or 2 steps with no repeat? Your model was too clever. Add one more line in the same .env file: ASKIT_MODEL=offline, save, and run again.
  3. Write what you saw in the Incident lines of submission\lab05_notes.md: how many steps? What does the tool keep answering? Why does the agent keep asking again?
  4. Switch the fix on. In agent.py press Ctrl+F, type STOP_ON_REPEAT, press Enter. Change False to True so the line reads STOP_ON_REPEAT = True and press Ctrl+S. (The agent now remembers each call it made. If it is about to make the exact same call again, it stops and a human takes over.)
  5. Run the same question again. It must stop after 2 steps.
  6. Clean up. Open .env again and delete the line ASKIT_INCIDENT=loop (and ASKIT_MODEL=offline if you added it). Save.
  7. Check: python check.py incident → 3 passed.
