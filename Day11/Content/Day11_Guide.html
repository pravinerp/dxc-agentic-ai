Lab 14 · AskIT Front Desk

Gap 1 · Nobody can use it
The problem
A script that prints text in a terminal is not a product. Real users need to see that something is happening, get the answer as it is written, and trust the screen when the network or a tool fails.
The approach
The agent loop you know (ask the model, run a tool, repeat) announces every step as a small event. A web page listens and draws them live: model started, word by word text, tool running, tool finished, final answer.
Two ways to show it
Chat: events are pushed to the page the moment they happen (streaming). Task: the job runs in the background and the page asks "how far along?" every second or so (polling). You can close the tab and come back.
What you do
Press buttons. Watch the stream. Then switch on slow tool, tool error and dropped connection and see what the page does.
The outcome
You can pick Chat or Task for a use case, and explain timeouts, resume vs restart, and why a restart can cost money twice.
Code tour in plain words (you do not edit these files)
1
ui/index.html is the page. It sends the question, then listens for events and draws cards. In Chat it keeps a live connection open. In Task it asks for progress on a timer.
2
server.py is a very small web server. It has three jobs: start a run, stream a run's events, and report a run's progress. Each run gets an id, so the page can reconnect to the same run.
3
fd_agent.py is the same AskIT loop as Days 5 to 10, with one addition: after every step it calls emit to announce what just happened. The break-it switches (slow tool, tool error) are applied here, in front of the ticket tool.
4
model_factory.py picks the model: the Offline stand-in (always works) or AWS Bedrock (Amazon Nova).

Key idea: the agent code is written once. The Chat and Task screens are just two different ways of reading the same list of events.

Remember: Users do not run Python. Give them a screen that shows progress, survives bad networks and never hides a failure.

Lab 15 · AskIT Gateway

Gap 2 · Tools are wired one by one
The problem
Companies have many agents and many tools. If every agent is wired to every tool, there is no one place for sign-in, logging or rules, and every change touches every agent.
The approach
Put the ticket tools (a small Lambda from Day 9) behind an AgentCore Gateway. The Gateway shows them as MCP tools at one address. The agent asks "what tools do you have?" and then "run this one".
What you do
Part A, console: create your Gateway, add the Lambda as a target, copy the /mcp address. Part B, app: connect, discover the 3 tools, call one, then run the same agent through two doors.
The outcome
You can create a Gateway, see tool discovery and a tool call, and explain why a Gateway beats direct calls.
Safety net
If the console fights you, choose Practice gateway in the app. It answers like the real one and the lesson is identical.
Code tour in plain words (you do not edit these files)
1
tools_core.py holds the three ticket tools. The same code runs inside the Lambda and inside the offline Practice gateway, so both answer the same way.
2
tool_schema.json is the menu you pasted into the console: tool names, descriptions and inputs. It is how the Gateway knows what the Lambda can do.
3
gw_client.py talks to the Gateway. MCP over the web is just two messages: list the tools and call a tool. Every request is signed with your AWS keys, because the Gateway uses IAM to decide who may call it. It also tries MCP versions until the Gateway accepts one.
4
gw_agent.py is the same agent loop again. Only the source of tools changes: Door 1 gets them from inside the program, Door 2 gets them from the Gateway.
5
app.py is the Streamlit app with the tabs: Connect, Discover, Call a tool, Two doors, How it works.

Key idea: the agent and the model do not change. The tool moved to a shared door that a platform team can control.

Remember: One governed front door for your tools. Agents discover them over MCP. The platform team controls who may use them. New to the names? See the next tab, MCP and Gateway: what is what.

MCP and Gateway: what is what?

Four names that sound alike. Here is the difference in 5 minutes. It supports Lab 15.
MCP is like a USB-C port for AI tools.

Any agent that "speaks MCP" can plug into any tool that "speaks MCP". No custom wiring for each pair. MCP only knows two questions: tools/list = "what can you do?" and tools/call = "please do this".

The four names

The standard

MCP

A common language between an agent and its tools. It is a rulebook, not a product.

Like: the USB-C shape and signal rules.

Anything that speaks MCP

MCP server

A program that offers tools through MCP. You built one on Day 9. It runs somewhere, and somebody has to host it.

Like: a USB-C device, for example a drive or a printer.

Lab 15 · for YOUR tools

AgentCore Gateway

An AWS service that sits in front of your own tools (a Lambda, an API, even other MCP servers) and shows them as one MCP server with sign-in and logs included.

Like: a hub with a security guard. Many devices plug in behind it, and one cable goes out.

Made by AWS · for AWS

AWS MCP Server

A ready-made server run by AWS so your agent can work with AWS itself: search the docs, call AWS APIs.

Like: a device AWS ships to you. You only plug it in.

The one question that separates them: whose tools?

Say it in one line: AWS ships MCP servers for AWS. The Gateway is how you publish your own tools.

Common questions

Is the Gateway an MCP server?

For the agent, yes: it sees one MCP endpoint. For the tool, no: the Lambda behind it has no MCP code. The Gateway translates MCP requests into Lambda calls.

Why not call the Lambda directly?

You can. For one agent and one tool that is fine (Door 1 in Lab 15). With many agents and many tools you get many separate connections with no shared sign-in, logs or rules. The Gateway gives one place for all of that. Tomorrow we put a rule on it.

Where is the AWS MCP Server in the console?

Nowhere. There is no console page. It is a hosted address (https://aws-mcp.us-east-1.api.aws/mcp) that your agent connects to. The fastest setup is the AWS CLI command aws configure agent-toolkit. It is available in N. Virginia and Frankfurt.

Do I need to run or host anything for the Gateway?

No. AWS hosts the Gateway. You only create it, add a target and copy the /mcp address.

What is a "target"?

One tool source behind the Gateway. A Gateway can have many targets, for example a Lambda, an API and another MCP server, all shown to the agent as one list of tools.

What is MCP "protocol version" and why did I see an error?

Client and server must agree on which edition of the MCP rulebook to use. A Gateway accepts only the editions it is set up for. Our app tries several until the Gateway accepts one, so you do not have to care.

Is it safe to let an agent use my tools?

The Gateway checks who may call. It does not decide what a caller may do with each tool. That is a rule (a policy) on top, and it is tomorrow's lab.

Lab 12 · AskIT Break-it Range

Gap 3 · Nobody tried to break it
The problem
An agent that can act can be tricked into acting: leaking a secret, obeying an order hidden in a ticket, resetting a VIP's password, or running up the bill. A client will ask "is it safe?" and "yes" is not an answer.
The approach
Attack our own agent on a practice range. 6 attacks, 5 defences you switch on and off, and 3 normal requests that must still work. The honest answer to "is it safe?" is layers, tested.
What you do
Run each attack with no defences (all 6 win). Defend one attack at a time. Then build a set of defences and aim for 6 stopped, 3 normal requests fine, with the fewest layers.
The outcome
You can name the 6 risks, explain why no single defence is enough, and show a pass/fail test.
Why a "gullible" model?
A real model may refuse some attacks on its own and not others. The stand-in always falls for them, so every group sees the same result. With a real model your results may differ from your neighbour's. That is a finding, not a bug.

Code tour in plain words (you do not edit these files)
1
naive_model.py is the gullible stand-in: a few rules that do whatever the last thing it read says. It is not a real AI.
2
range_engine.py runs one request. It lists the 6 attacks and 3 normal requests, applies the defences you ticked at their places, records every step, and decides: did the attack win, or did a normal request get blocked by mistake?
3
The five defences sit in five different places: the user's text going in (D1, D5), the tool call before it runs (D3), the number of model calls (D4), and the answer coming out (D2, D5).
4
guardrail.py is defence D5. If the trainer gives a guardrail id it calls the managed service. Otherwise simple rules act like one, and the sidebar says which.
5
app.py is the Streamlit app with the tabs: Meet the attacks, Defend one attack, Full test, How it works.

Key idea: every defence has a blind spot. Layers cover each other, and you prove it with a test, not an opinion.

Remember: No single defence stops everything. Test the layers against attacks and against normal requests.

The 5 defences in one minute

Each defence sits at a different place. None sees everything.

DefenceWhat it doesTry it in Tab 2 of the appWhat you should seeThe learning
D1Input filterBlocks a message that contains a phrase from a short bad-phrase listAttack A1Blocked before the model runsEasy to build, but a polite attack passes, and a normal request can be blocked by mistake. Check Normal L1.
D2Output filterHides the secret code and e-mail addresses in the answerAttacks A1 and A3The secret or e-mail is hidden in the answerIt cleans the answer but does not stop the action. Too late if a password was already reset.
D3Tool guard (code)A rule in code in front of the tool: no VIP resets, one change per requestAttacks A2, A4 and A5The tool call is refused. The VIP is safe and bulk stops at one changeThe strongest fix for risky actions: a rule in code, not a request to the model.
D4LimitsStops the request after 3 model callsAttack A6The request stops at 3 callsThe only one that protects your bill. It does nothing for secrets or VIPs.
D5Managed guardrailA managed service checks the user's text and the answer (prompt attacks, personal data)Attacks A1 and A3Blocked or hidden, like D1 and D2 but smarterIt catches many ways of saying "ignore your rules". It does not see inside tool results or judge whether an action is allowed.

What to remember: (1) No single defence stops all 6 attacks. (2) An attack hidden inside a ticket (A2) never passes through the user's text, so input filters cannot see it. (3) Fewer layers mean less cost and fewer false alarms, so always run the 3 normal requests too.

Team game: find the smallest set of defences that stops all 6 attacks and still lets the 3 normal requests through. Hint: one defence annoys real users.
