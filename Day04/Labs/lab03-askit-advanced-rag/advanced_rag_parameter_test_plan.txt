PURPOSE
-------
Use one engineered knowledge file to make Advanced RAG controls visibly change what is retrieved and what the LLM can answer.
For metadata/audience filtering, use the lab's PRELOADED AskIT KB because audience/status metadata is document-level and cannot be honestly demonstrated inside one uploaded document.

IMPORTANT SCORE LEGEND FOR THIS LAB
-----------------------------------
Do NOT assume every "score" is cosine similarity.

Search = keyword:
- retrieval score = normalized BM25 keyword score (0-1)
- top result often shows 1.0 because BM25 scores are normalized against the best result

Search = vector:
- retrieval score = cosine similarity from embeddings

Search = hybrid:
- retrieval score = normalized Reciprocal Rank Fusion (RRF) score combining keyword rank + vector rank
- this is NOT cosine similarity

Reranker OFF:
- final score = retrieval score

Reranker ON (live Bedrock/OpenAI):
- final score = LLM reranker relevance score (0-1)
- retrieval column still shows the original keyword/vector/hybrid score

Term coverage:
- fraction of meaningful query terms that literally occur in the chunk

Guard relevance in THIS lab:
- reranker ON + live provider -> guard uses reranker final score
- reranker OFF -> guard uses term coverage
This is important: Guard Threshold is not always a cosine threshold.

INDEXING BEHAVIOUR
------------------
Unlike the earlier basic RAG lab, you do NOT need to re-upload the file whenever chunking changes.
The app stores the parsed document and builds/caches a new index automatically for a new:
- chunking strategy
- chunk size
- overlap
- provider / embedding model
- document source

Changing Search / Metadata Filter / Reranker / Top-K / Guard does not require re-uploading.

TEST 1 — SECTION CHUNKING vs FIXED CHUNKING
=================================================

Question:
My SecureDesk error 417 is still there after the basic checks. What should I do next?

TEST 1A — FIXED
Chunking = fixed
Chunk size = 180
Overlap = 0
Search = keyword
Metadata filter = ON
Reranker = OFF
Top-K = 1
Guard = OFF

EXPECTED:
The best fixed chunk strongly matches "error 417 / basic checks" but ends before the full ORBIT-B answer.
The LLM should be unable to confidently state ORBIT-B from that one chunk.

TEACH:
Fixed-size chunking respects character boundaries, not logical document structure.
A relevant chunk can stop just before the answer.

TEST 1B — SECTION
Change ONLY:
Chunking = section

Ask the SAME question.

EXPECTED:
The whole "SecureDesk Error 417 Recovery" section is one chunk and includes:
Switch the gateway to ORBIT-B.
The answer should now be clear with Top-K = 1.

TEACH:
Section chunking uses document structure/meaning boundaries rather than arbitrary character windows.

EXPECTED:
0.67 < 0.70 -> pipeline abstains BEFORE generation.

=================================================
FINAL PIPELINE MENTAL MODEL
=================================================

1. SOURCE + METADATA FILTER
   Which documents/chunks are eligible?

2. CHUNKING
   What units of evidence exist?

3. SEARCH
   Which chunks become candidates?
   - keyword
   - vector
   - hybrid

4. RERANKER
   Which candidates actually answer the question best?

5. TOP-K
   How many final chunks reach generation?

6. GUARD
   Is the evidence strong enough to answer at all?

7. LLM GENERATOR
   Read the selected evidence and formulate the grounded response.

Best class line:
"Retrieval finds candidates. Reranking improves the order. Top-K controls what reaches the LLM. The guard decides whether the evidence is strong enough to answer."

=================================================
OPERATIONAL CONTROLS (NOT THE MAIN RAG LOGIC)
=================================================

Provider / embedding model:
Can change vector rankings, cost and latency.
Changing embedding model requires a different vector index.

Chat model:
Can change reranker/generation quality, cost and latency.

Documents to search:
Changes the corpus itself; naturally changes all rankings.

Compare with baseline:
Runs a second pipeline for teaching/comparison; it is not itself a retrieval algorithm.
