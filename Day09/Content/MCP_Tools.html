Idea 1 · Why MCP

Tools should be written once and shared

Until now every agent had its tool functions inside its own code. With 5 agents and 6 systems that is 30 hand-made connections, each with its own logging, security and bugs. MCP (Model Context Protocol) is a standard way for an agent to ask a server: who are you, what tools do you have, please call this one.

Without MCP: 3 agents × 3 tools = 9 hand-made connections.
With MCP: 3 + 1 connections. A 4th agent adds ONE.
Function calling (Day 5)REST APIMCP
Who defines the tool?Inside each agent's codeA service, documented for developersA server, described for AI agents
Discoverable by an agent at run time?NoOnly if someone reads the docsYes: tools/list
Shared by many agents?Copy the codeYes, every agent writes its own clientYes: one standard client
Say this: "MCP does for AI tools what USB did for devices: one plug, any agent, any tool."
Quick check · Idea 1

Three questions

1. 5 agents need 6 systems. With no MCP, how many connections are built?
5 × 6 = 30 (N × M). With MCP each system has one server and each agent one client: 5 + 6 = 11.
2. Which message tells the agent WHAT the server can do?
tools/list returns names, descriptions and input schemas. The model decides from these.
3. Why can a simple Lambda function be an MCP server in the newest version?
Every message stands alone, so any web function that answers JSON can serve MCP.
Idea 2 · Descriptions and controls

The model only sees descriptions. You control the rest.

The agent never reads your tool code. It chooses a tool by its name and description. A bad description means a wrong tool, and a wrong tool is a real incident (a password reset instead of a lookup).

Where can a control live?GoodRisk
In each agent (client side)Quick to start; the agent knows its own userA careless team forgets it
Inside the MCP serverEveryone gets it, enforced in one placeThe server team must own security
In a gateway in front (production)Central policy, audit and identityOne more service to run
Golden rule: controls go around the tools, in plain code. Never rely on “please be careful” in a prompt.
Quick check · Idea 2

Three questions

1. Two tools have almost the same description. What happens?
The model never sees the code. Distinct, specific descriptions are your main defence.
2. Strict masking hides employee ids. What is the cost?
Masking is a trade-off between privacy and usefulness. Decide per field.
3. The CISO says: every agent team must log calls, and we do not trust them to remember. Best home for the control?
Enforce it once, where agents cannot skip it.
Idea 3 · Homes for a tool server

Same agent, same tools: only the home changes

The same agent on three homes. Lab 9 runs all three.
Stdio on a VMHTTP on a VM or containerAWS Lambda
Who can call itOnly the program that started itAny client that can reach the portAnyone with URL + identity
Good forYour laptop, VS Code, desktop toolsA shared team serverCloud-native, spiky usage, no ops
Weak atSharingYou patch and monitor itPrivate networks, long jobs, cold starts
Say this: "We write the tools once. Where they run is a deployment choice, not a rewrite."
Quick check · Idea 3

Three questions

1. The first Lambda call took 900 ms, the next ones 30 ms. Why?
After idle time Lambda starts a new instance. Pay that wait only after quiet periods.
2. A Function URL with auth NONE and no key is...
HTTPS hides the traffic, not who can call. Always add an identity check.
3. The ticket system is inside the client's data centre with no internet address. Where should the MCP server run?
Put the server next to the system it protects.
Before the lab · How the app works

What happens behind the MCP Control Room

One Streamlit app, one question. Follow the numbers.

The app you will use. Tab 1 shows steps 4–5, tab 2 steps 1–6, tab 4 step 3, tab 5 moves step 5 to AWS.
  1. You ask a question, for example “What is the status of TKT-0004?”. app.py
  2. The agent reads the tool descriptions (from tools/list) and picks a tool and its inputs. run_agent()
  3. The controls run in plain code: role and VIP check, timeout and retry, masking, logging. guarded_call()
  4. The MCP client sends the JSON message over the chosen home (pipe, HTTP or HTTPS). mcp_client.py
  5. The MCP server runs the tool and answers. Tab 1 shows each message in the wire log. askit_server.py
  6. The tool is the same function as Days 5–8. askit_core/tools.py
  7. The answer goes back up, masked on the way. The model writes the reply.

Lab 9 · Part C · Your own MCP server on AWS Lambda (tab 5)

We are still in Lab 9 · lab09-askit-mcp-control-room. App tab 5 · Move to AWS shows these steps; the AWS console is in another browser tab.

What we doUpload the data to S3, create a Lambda function, upload the code zip, set the settings, create the URL, connect the app to it.
WhyShowing MCP on AWS is a sales demo, and AWS is where Days 10–12 go.
OutcomeThe SAME agent from tab 2 answers using tools that live in YOUR AWS function.
How9 console steps with your user name, then 3 buttons in the app.
  1. Sign in to the AWS console as your user. Check the region: N. Virginia.
  2. S3: open bucket devproacademy-askit-data-868859238853 > Create folder named your user name > open it > Upload > Add folder > C:\AskIT\dxc-agentic-ai\askit_data > Upload. Check you see askit_data/ with tickets.csv, users.csv, kb/.
  3. Lambda > Create function > Event function > Author from scratch. Name user1NN-askit-mcp (your number). Runtime Python 3.13 (change it if it says Node.js).
  4. Additional settings > Custom execution role on > askit-lambda-role. Create function.
  5. Code > Upload from > .zip file (not the S3 location option): aws\askit-mcp-lambda.zip in the lab folder. Save. It holds code only.
  6. Configuration > Environment variables, add three: ASKIT_KEY = your user name, ASKIT_BUCKET = devproacademy-askit-data-868859238853, ASKIT_PREFIX = user1NN/askit_data/ (with the slash at the end).
  7. Configuration > General configuration > Edit: Timeout 30 sec, Memory 256 MB. Save.
  8. Configuration > Function URL > Create, auth NONE. Copy the URL.
  9. App tab 5: paste URL and key, 💾 Save, ✅ Test my Lambda.
  10. ⏱️ Call it 3 times: which call is slowest, and why? Then ➡️ Use Lambda as my tool home and repeat tab 2.
  11. In AWS: Monitor > View CloudWatch logs. Find your own calls.
⚡ Fast movers: open askit_data\kb\KB-004_vpn_connect.md on your PC, change one line, save. Upload it again to your-user-name/askit_data/kb/ in S3 (same name). Wait 10 seconds, ask the VPN question again in tab 2. Your change appears and you never touched the function: data and code are separate.

Time: 45 minutes. 401 = key mismatch. 403 = URL auth must be NONE. 404 = wrong URL. 502 = look at the logs (a timeout line means step 7 was missed). "ASKIT_BUCKET is not set" or no data = step 6 (check the prefix, it ends with a slash).

Incident · “The ticket tool is slow” (tab 6)

Same app, tab 6 · Incident. Pick any home.

What we doMake the server slow and flaky, then tune the client's timeout and retries.
WhyOn Monday mornings real systems are slow. Agents that hang cost money.
OutcomeSettings that finish in 8 seconds even when the first 2 calls fail.
HowFour sliders and one button.
  1. Server slow by 6 s, client waits 3 s, no retries. Press ▶ Call get_ticket. Read the attempts.
  2. Mission: server fails the first 2 calls. Find timeout and retries that finish in under 8 seconds.
  3. For Lambda: change ASKIT_DELAY and the function Timeout in the console.

Time: 15 minutes.
